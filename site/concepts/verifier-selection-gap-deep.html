The verifier selection gap — generating many answers and picking the right one are different jobs

A model can produce a pile of candidate answers, and the right one might be in there. But finding it is a separate, harder problem from generating it. Here is why: the numbers from a real run where voting reaches 57% but a single pick is only 39–43%, and four different graders score the same answers 0% / 64% / 40% / 44%. The gap is where selection happens, and this is where almost all of self-improvement lives.

1 · The problem — generating an answer is not the same as picking the right one

A model can produce many candidate answers for a single hard question. Sometimes the right answer is in that pile. But recognizing which one is right is a separate job from creating the candidates in the first place.

This matters because the honest question is not ‘can the model write a correct answer somewhere?’ but rather ‘will the system hand me back the correct answer?’ The answer depends not only on whether the model can reach the right one, but whether something can reliably pick it from the pile.

2 · The reframe — coverage is not the same as accuracy

Call coverage the ability to produce the right answer at least once in a batch of tries. Call selection accuracy the ability to pick the right one from the batch. A system can have high coverage — the right answer appears in 8 out of 10 tries — but still pick wrong if the selector is broken. Sampling more to raise coverage does nothing if the selector does not improve.

This is the gap: your generator and your selector are separate machines working on separate problems.

The hidden quantity is the selection gap — the difference between the right answer being somewhere in the samples and actually being picked out; most of the room to improve lives there.

3 · Seen on a real run — coverage says it is reachable but selection still fails

We ran a real 0.6-billion-parameter model (Qwen3-0.6B — small on purpose, so it is unsure) on 14 grade-school math problems. We took 8 tries per problem. Every number below is measured.

selection methodaccuracy
pick a single random answer39%
pick the greedy (careful, temperature-0) answer43%
pick by majority vote of the 8 sampled answers57%

The key: the majority-vote result (57%) is the ceiling for that pile of answers. It tells us the right answer appears in the pile at least 57% of the time. But a single picked answer reaches only 39–43%. This is the gap.

The discovered fact: a system that can generate the right answer 57% of the time might still hand back the wrong answer 57–61% of the time if the picker is dumb. Majority voting has zero idea which answer is truly right — it only counts which is most popular. But it beats a random pick and even beats the model's own confident best guess.

4 · Why the gap exists — the grader is itself unreliable

Now suppose you build a verifier — a separate model trained to score which answers are correct. You run it on the same 25 traced problems to see how well it picks. But you need to define what ‘correct’ means. The problem is: how you score the answer is a choice, and different choices give different scores.

We tested four grading rules on the identical 25 traces:

grading rulescore
exact string match of the final answer0%
does the right number appear anywhere in the text?64%
does the last number in the text match?40%
is there a clean boxed final answer that matches?44%
A verifier cannot be better than the signal it learns from. If you train it on a lenient rule (64%), it learns to value wrong answers that happen to mention the right number in passing. If you train it on a careful rule (44%), it learns something narrower but trustworthy. The grader design is a choice that limits what the verifier can be.

5 · The one real weakness — the verifier is itself a model that can be wrong

A verifier is just another model, scored on pairs of (answer, ground-truth label). It sees correlations — maybe correct answers are often longer, or mention certain keywords. But those correlations can be spurious. If the training data happens to have mostly long correct answers and short wrong ones, the verifier learns ‘long = right’ even if that is not the deep cause.

This means a verifier can be confidently wrong. It hands back a high score for an answer that is plausible, well-written, and utterly incorrect. And because it is confident, the system trusts it. A bad verifier is worse than no verifier — it actively misguides the whole pipeline.

6 · The surprise — the verifier selection gap is the core of self-improvement

This is why the rest of the course exists. Every technique that follows — reward models, process supervision, constitutional critique, RL training — is trying to close this gap. The goal is always the same: build a better selector.

If you can sample 100 answers and the right one appears in 80 of them (coverage = 80%), your system is wasted if the selector picks wrong 70% of the time. Raising the model's generation ceiling is useless without raising the selection accuracy to match. The hard part of self-improvement is not generating more candidates — it is reliably picking the good one.

7 · Where it is used in practice — Generating an answer and picking the right one are different problems

A model can produce many candidates—some right, some wrong. The hard part is not generating the pile but finding the right one in it. A system might sample many completions in a coder agent, try many proof paths in a theorem prover, or generate multiple math solutions. But if the selector is weak, the system hands back the wrong answer even though the right one was in the pile. Majority voting beats random guessing but beats single greedy picks too.

Coverage is the ceiling—does the right answer appear at least once in all attempts? Selection accuracy is what the user sees—does the system hand back the correct one? A verifier or voting rule bridges the gap, but it has its own failure modes. If the verifier is trained on a faulty signal or overfits to training data, it picks wrong confidently. The gap widens when the verifier and generator are mismatched.

Self-improvement is bottlenecked by selection, not generation; raising coverage alone is wasted if the picker fails.

the run recipe — reproduce every number above

Qwen3-0.6B on 14 GSM8K grade-school math problems, Colab L4 GPU. For each problem: generate 8 sampled answers at temperature 0.9, plus one greedy answer at temperature 0. Select by (a) random pick, (b) greedy, (c) majority vote of the 8 samples. Separately, take 25 traces and score them four ways: exact string match, number anywhere in text, last number in text, boxed final answer. Grader = careful boxed-answer check.

# Coverage vs selection accuracy for each problem: samples[1..8] = model(question, temperature=0.9) greedy = model(question, temperature=0) random_pick = choice(samples) # one random sample majority_vote = most_common(final_number(s) for s in samples) # Results on 14 problems: # random pick: 39% (39 accuracy) # greedy pick: 43% (43 accuracy) # majority-vote pick: 57% (57 accuracy / coverage ceiling of the pile) # Grader reliability on 25 traces: # exact match: 0/25 = 0% # number anywhere: 16/25 = 64% # last number: 10/25 = 40% # boxed answer: 11/25 = 44%
