Task Specification

Task specification turns a vague user request into a concrete goal, constraints, success criteria, and verification plan.

Ordinary Problem

Users often underspecify what they want, what sources are allowed, or what counts as done.

Naive Picture

Start acting immediately from the first user sentence.

Why It Fails

The agent may optimize the wrong target, search the wrong space, or stop before the real task is complete.

First-Principles Move

Before acting, the agent needs a contract: goal, assumptions, allowed actions, evidence standards, and stopping rule.

What Breaks Without It

End-to-end automation becomes unreliable because completion is undefined.

Course Role

Part 1 connects goals and stopping conditions to the definition of agents.

Worked Example

A user asks a coding agent: "Fix the bug in my test file." This is underspecified. The agent must first clarify the task before acting. Specification dialogue: Agent asks, "Which file?" User: "tests/test_auth.py." Agent asks, "What is the expected behavior?" User: "Login should return a 200 status code, but it returns 401." Agent specifies the task: GOAL = "Modify tests/test_auth.py so that the test_login function passes when the login endpoint returns a 200 status code." ALLOWED_ACTIONS = {read_file, run_test, edit_file, search_docs, run_command}. SUCCESS_CRITERIA = "test_login passes when login endpoint returns 200; agent does not modify production code."

STOPPING_RULE = "Stop when test passes and is committed, or when agent determines the test cannot be fixed without changing production code." Now the agent reads the file (40 lines), runs the test (fails with "AssertionError: 401 != 200"), edits the test's expected value from 401 to 200, runs the test again (passes), and stops because the stopping rule is satisfied. Total time: 12 seconds; clarity prevented 5+ minutes of blind action-taking.

One Level Deeper

Task specification is a contract consisting of five predicates that define the agent's problem space. (1) GOAL: a logical formula or success predicate that maps states to True when achieved. For the test fix, GOAL(s) = test_login_passes(s) AND unchanged(production_code, s). (2) CONSTRAINTS or ALLOWED_ACTIONS: the set of operations the agent can call. If the agent tries to call delete_file, it violates the constraint set. (3) SUCCESS_CRITERIA: the observable evidence that GOAL was achieved. Is a passing test enough, or must the fix also pass code review?

(4) EVIDENCE_STANDARD: what counts as proof. A passing test in CI/CD counts more strongly than a local test run if the environment is flaky. (5) STOPPING_RULE: a termination condition stop_time(s) = True when the agent should halt. Examples: "after 5 minutes, stop," "after 3 failed attempts to fix the test, escalate to a human." Once these five elements are explicit, the agent's behavior becomes predictable and auditable. Changes to any element require re-specification: if ALLOWED_ACTIONS omits run_test, the agent cannot verify its edits in-loop.

Failure Boundary

Task specification becomes unreliable when any of the five predicates is vague or conflicting. If GOAL is imprecise ("make the test better"), the agent may optimize metrics that do not align with user intent: it might simplify the test to trivial assertions that always pass, achieving "test passes" without achieving "code is reliable." If CONSTRAINTS are underspecified, the agent may access forbidden tools: allowed actions say {read_file, edit_file} but not run_shell, yet the agent finds a way to call shell via an API. If SUCCESS_CRITERIA are observable but loose ("the user is happy"), the agent will stop after the first change without confidence that it is correct, because happiness is not measurable.

If EVIDENCE_STANDARD is mismatched to reality (agent believes a local test pass is proof, but the CI/CD environment has different dependencies), the agent will commit a broken fix. If STOPPING_RULE is absent or recursive ("stop when done, where done means stop"), the agent may loop indefinitely. A fourth failure mode occurs when the task is impossible: GOAL asks for status code 200, but the production API has a bug that forces 401; CONSTRAINTS forbid editing production code. The agent will exhaust all allowed actions, discover the goal is unreachable, but then may restart the loop in frustration or report failure unclearly. Observable symptoms: agent repeats the same edit-test cycle 3+ times with no progress, or agent produces an answer that does not satisfy any stated criteria but claims success anyway.
