Inference Budgeting

Inference budgeting is deciding how much runtime compute to spend on a problem and where to spend it.

Ordinary Problem

More samples, deeper search, and more verifier calls can improve quality but cost time and money.

Naive Picture

Always generate as many candidates as possible whenever a problem looks difficult.

Why It Fails

Some tasks are easy, some are hard, and compute spent on low-value branches cannot be spent elsewhere.

First-Principles Move

A system should allocate compute where the expected value of another attempt exceeds its cost. Difficulty estimation, confidence, verifier feedback, and search state guide that allocation.

What Breaks Without It

The agent becomes too slow, too expensive, or still unreliable because compute is spent in the wrong places.

Course Role

This is the operational constraint behind test-time scaling.

Worked Example

Suppose you have a $100 budget for inference compute (cost per token × total tokens). On a mixed problem set, easy problems (pass@1 = 80%) might only need 1–2 samples to solve, costing $1–2 per problem. Hard problems (pass@1 = 5%) might need 100–200 samples, costing $50–100 per problem. Allocating a fixed $2 budget per problem wastes money on easy ones (solve on first try) and fails on hard ones (too few samples). Smart budgeting: spend $1 per easy problem (1 sample) and $15 per hard problem (50 samples), adjusting per estimated difficulty.

The transcript's Archon framework shows this concretely: given a budget of 8 model calls total, Archon searches different inference-time architectures (parallel samples, sequential revisions, fusion, critics). It finds that for coding problems, generating 8 samples + running unit tests + fusing is better than generating 1 high-quality sample. But on simpler tasks, sequential refinement (asking the model to revise its own answer) beats parallel sampling, because one good path is easier to improve than finding a needle in a haystack of parallel attempts.

One Level Deeper

Inference budgeting is an optimization problem: given a budget B (tokens, cost, or latency), choose allocations (n_parallel, n_sequential, n_verifier_calls) to maximize quality (expected accuracy).

For a single problem with estimated difficulty d (derived from model confidence or prior pass@1), the expected value of an additional sample is: EV(sample) = Pr(new sample is correct | previous samples) × value_of_correctness - cost_of_sample. If EV > 0, spend the budget; otherwise, stop. A process reward model or confidence estimate can guide this decision: if the PRM gives high scores to current best-guess, spending more samples has low EV. A Bayesian approach uses prior beliefs about problem difficulty to set initial budgets, then updates based on intermediate results (e.g., "we have 200 samples and none are correct → this problem is harder than expected → allocate more").

Difficulty estimation can come from: (1) model confidence (higher temperature sampling = lower confidence), (2) PRM or ORM scores on initial samples, (3) past performance on similar problems. The lecture shows that harder problems benefit from more sequential tokens (deeper reasoning per sample) while easier ones benefit from more parallel samples (coverage).

Failure Boundary

Inference budgeting fails when difficulty estimation is inaccurate. If the system overestimates easy problems as hard, it wastes budget on unnecessary samples. If it underestimates hard problems, it stops too early and fails. This is particularly acute in new domains where the model has never been tested and priors are weak.

Second, the value function (utility of solving a problem) may not be uniform. In a real system, some queries are higher priority and worth more spend. Greedy per-problem budgeting ignores this and allocates equally across all problems, suboptimally. Third, some problems may have diminishing returns: after 20 samples, each new sample contributes less probability mass of correctness, making additional spending wasteful. Finally, the assumption that samples are independent and identically distributed breaks down in correlated error modes (as noted above). A robust budget allocator must handle structured failure and model-specific biases, not just statistical variance.
