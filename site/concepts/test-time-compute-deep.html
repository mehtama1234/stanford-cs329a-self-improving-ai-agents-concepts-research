Test-time compute — a fixed model gets better if you let it work harder at each answer

A trained model has a ceiling on what it can reach on any single try. But you can spend more compute at answer time and still raise the answer's correctness — by thinking longer, or by trying many times and picking the best. Neither requires retraining. Here is the idea, two real ways it works, why the gains flatten, when it fails, and where it reappears in reasoning models and inference budgeting.

1 · The problem — a single attempt has a fixed skill ceiling

Train a model and freeze it. One forward pass, one answer. That answer carries the model's single-try accuracy on that question — and the model can do no better than that by itself, because the weights never move again.

But The hidden fact: the model's skill is not really fixed. It is only fixed per attempt. What if the model could work on the question for longer? What if it could try many times and pick the best? The model's knowledge is still the same, but how hard you make it work at answer time can still raise the answer quality.

2 · The reframe — spend inference compute, not training compute

This move is called test-time compute — paying for more inference (answering), not more training (learning). You have two main levers:

1. Make the model think longer. Instead of rushing to a conclusion, let it write out step-by-step reasoning, intermediate checks, or refined guesses. Give it a token budget and let it use it. The longer chain costs more compute but often lands on better answers.

2. Try many times and aggregate. Run the same question through the model several times with a little randomness turned on, so each try explores a different chain. Collect all the answers, then vote, average, or search among them. Whichever answer the model reaches most often is usually the right one.

Both are ways to spend inference tokens without touching the model's weights. They work because the model's knowledge exists in the frozen weights, but finding that knowledge requires search or exploration, and you can buy more search with more compute.

3 · Seen on a real run — longer thinking and voting both lift the answer

We ran a real 0.6-billion-parameter model (Qwen3-0.6B) on two sets of grade-school math word problems (GSM8K). For each we measured what happened when we spent more inference compute.

Test 1: Longer thinking. A quick direct answer is right 47% of the time. Let the model think first, working through the problem step-by-step before answering, it reaches 60% — same model, same weights, just more tokens spent.

Test 2: Many tries plus voting. A single greedy answer is right 43% of the time. Take the same question, sample it 8 times with temperature turned up (so each try is noisy), then vote on the final number. The vote says 57% — again, same frozen model, just more inference budget.

The gains are real but not unlimited — a model that misses 40% of hard problems cannot simply think its way to 95%.

4 · Why both work — and why they stop helping

Start with thinking. A model's reasoning is not instant; it is a chain of steps, each building on the last. A quick answer runs this chain in a rush, committing to the first plausible path it finds. A longer chain lets it backtrack, reconsider, spot its own mistakes. More tokens = more room to explore the reasoning space before settling.

Now sampling. A frozen model generates answers by rolling dice at each token. A single roll is noisy — a bad roll early can lock in a wrong path. But multiple independent rolls of the same question explore different chains. If the right answer lives somewhere in the model's knowledge, many tries increase the chance that at least one try reaches it. The vote finds it.

But both hit a wall. If the model genuinely does not know the answer — it has never seen a similar problem, or the knowledge was never learned — then no amount of thinking or sampling can reach it. The reasoning goes in circles; the samples never land on the right answer. That is why both curves flatten: after the model has explored what it can reach, extra tokens and extra tries just re-generate answers it has already tried.

5 · The one real weakness — you cannot buy accuracy above the model's ceiling

Test-time compute is a tool, not a miracle. It works because the model's knowledge includes the right answer somewhere in its possibility space. If the model has never learned a skill, no amount of inference time will conjure it.

A concrete failure: if a model answers a problem wrong on every single try — it is systematically confidently wrong — then voting will faithfully return the wrong answer, and more sampling makes the vote more certain of that wrongness, not less. You are paying more compute for a wrong answer you were already getting.

There is also the cost angle. Every extra token and every extra attempt costs real GPU time and real money. If you are spending 8 times the compute to lift accuracy by 14 points (43% to 57%), you are paying heavily for shrinking gains. The inference budget is not infinite.

6 · The surprise — reasoning models are built on this axis

The same idea reappears at every scale. On large models (Llama 3-70B, GPT-4) one attempt solves hard math at 20-45% accuracy. Generate 100 or 1000 samples and use a verifier to pick the best: now it solves 50-70% of problems. No retraining. The entire gain comes from test-time compute — pass@k (the probability that the right answer appears in any of k tries) is the standard way to measure this.

Reasoning models like OpenAI's o1 push this even further: their entire architecture is designed to spend more tokens on harder questions. They do not have bigger weights than base models; they have more tokens, more thinking, more test-time compute. The log-linear scaling you see on benchmarks (accuracy climbs by 10–20 points for every 10-fold increase in inference tokens) is this same axis.

This is what separates a reasoning model from a chatbot. A chatbot makes one fast pass. A reasoning model budgets its inference time — spend more on what needs it. That budget is test-time compute. And the deeper methods all feed on it: verifiers pick from the samples, reinforcement learning rewards the good ones, retrieval feeds them relevant context. They all start by generating a pool to choose from. Get many tries first; everything else is about choosing among them well.

7 · Where it is used in practice — Pay for thinking, not retraining

Reasoning models like o1 and o3 spend extra inference time on hard problems, letting them write out thought chains before answering. Code assistants use the same idea—sample multiple completions and pick the best. Theorem provers like Lean verifiers run many proof attempts and use search to find the one that reaches the goal. In all cases, the base model stays frozen; only the inference compute changes.

A verifier watches the outputs and picks winners, or a majority vote counts which answer appears most often. When the budget is large enough, the right answer tends to rise to the top. The trade-off is pure arithmetic: more attempts or longer thinking cost more GPU time but buy accuracy without changing the model's weights.

Reasoning models are built on this axis—their entire gain comes from test-time compute, not model size.
