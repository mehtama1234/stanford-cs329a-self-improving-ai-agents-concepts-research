Execution Feedback

Execution feedback means running generated code or actions and using the result as a correction signal.

Ordinary Problem

Code can look plausible while failing at runtime or producing the wrong output.

Naive Picture

Judge code by reading it or by model confidence.

Why It Fails

Execution reveals failures that prose review can miss: syntax errors, failing tests, wrong outputs, timeouts, and state mistakes.

First-Principles Move

When a domain can be executed, the environment can provide objective feedback. That feedback can guide repair, selection, or training.

What Breaks Without It

The agent keeps producing plausible code without grounding it in behavior.

Course Role

Part 4 uses code feedback as a concrete self-improvement channel.

Worked Example

A coding agent is asked to solve a palindrome-detection problem. In Turn 1, it generates a basic solution but the public test execution reveals a timeout error (execution failures detected in the environment). The model receives this feedback—the specific error message and stack trace—as structured input. In Turn 2, it generates an optimized solution using the error trace. This time the public tests pass (all test outputs succeed). The solution then advances to a private test set, which determines a binary reward: 1 for passing, 0 for failing. Across multiple iterations (Turn 1 → Turn 2 → Turn 3), the model repairs its outputs by targeting the errors it observes. With each failed attempt revealing which specific code paths broke (wrong output type, timeout, logic error), the model builds a learned pattern: these error types correlate with these kinds of fixes.

One Level Deeper

Execution feedback creates a structured loop where (1) the model generates code tokens sequentially, (2) a runtime environment executes that code and returns typed output (pass/fail status, error message, assertion failure), and (3) that feedback is appended to the context as the next input prompt. The reward is binary—R(trajectory) ∈ {0, 1}—but obtained through real execution semantics, not approximation. During RL training with PPO, two key design choices matter: (a) a two-tier test strategy (public tests for fast iteration feedback; private tests for final reward only) prevents overfitting to test signals, and (b) token-level policy gradient (actor updates per-token, but value function computed at trajectory level) gives finer-grained exploration than full-trajectory-level updates. The advantage A(t) is estimated by comparing the private reward against a baseline, allowing the model to learn which token-level edits correlate with error repair.

Failure Boundary

Execution feedback stops being trustworthy when the reward signal becomes too sparse or noisy. If nearly all generated code fails initially, the model sees almost zero positive rewards and has no hill-climbing signal—the learning becomes unstable. Similarly, if the underlying execution environment is unreliable (flaky tests, non-deterministic timeouts, non-deterministic results), the model optimizes against noise rather than true error patterns and may learn to exploit timing variance rather than fix logic errors. Finally, on sufficiently complex problems, binary reward alone may not guide repair; a solution generating the wrong output type at line 500 receives identical feedback to one failing at line 100, making credit assignment impossible. In these cases, richer feedback (error traces, step-by-step test output) or process reward models become necessary.
