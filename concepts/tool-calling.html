tools

Tool Calling

Tool calling lets the model request work from outside itself: search, code execution, calculators, APIs, files, databases, or other services.

Ordinary Problem

Text-only reasoning cannot directly observe the world, run a test, query a database, or change a file.

Naive Picture

The LLM should answer everything from its internal knowledge.

Why It Fails

Internal knowledge may be stale, unverifiable, or insufficient for tasks requiring action.

First-Principles Move

A tool extends the agent's action space. The model proposes an action; the environment returns an observation; the next step should depend on that observation.

What Breaks Without It

The agent remains a commentator rather than a worker.

Course Role

Part 4 and the recap identify tool use as central to end-to-end workflows.

Worked Example

You ask a model: "What is the temperature today in San Francisco?" Without tools, the model generates text: "It is probably around 70 degrees based on typical weather in September." It hallucinates because it has no current information—its training data is months old.

With tool calling, the model generates a structured request: [TOOL_CALL: SearchWeather(location="San Francisco", time="today")]. The system executes this, getting back: "San Francisco weather: 65°F, partly cloudy." The model now generates a grounded response: "The current temperature in San Francisco is 65 degrees Fahrenheit and it is partly cloudy." The tool call lets the model ground its answer in real-world facts.

Another example: you ask to buy a nightstand. The model generates [TOOL_CALL: Search(query="nightstand with drawers")]. It receives a list of products. It checks the first one [TOOL_CALL: AddToCart(product_id=123)], then [TOOL_CALL: Checkout()]. Each tool call receives an observation (product info, confirmation number), and the next action depends on it.

One Level Deeper

Tool calling is the mechanism where the model outputs a structured action: a_t = π(s_t | θ), where s_t is the current state (query + prior observations) and π is the policy. The action space is discrete: {Search, AddToCart, ViewProduct, Checkout, ...}. Each action a_t → observation o_t. The model's next state is s_{t+1} = (s_t, a_t, o_t).

Implementation: the model generates tokens that encode the tool call (e.g., via JSON or special tokens). A parser extracts (tool_name, arguments). The system executes the tool and returns (observation, success_flag). This observation is appended to context. The model continues generating the next action or reasoning step. This is distinct from pure generation because execution provides objective feedback—did the tool work? What did it return? This breaks the model's dependence on internal knowledge alone. The framework treats the agent as a Markov process: each action depends on current state (all prior observations), and the environment responds deterministically.

Failure Boundary

Tool calling fails when the model hallucinates tool names or arguments. For example, the model generates [TOOL_CALL: Search(query=undefined)], passing an invalid argument. The tool returns an error or empty result. If the model is not trained to handle errors gracefully, it may enter a loop: calling the same invalid tool repeatedly or generating nonsensical follow-ups.

Another failure: the model calls tools unnecessarily. For simple questions like "1 + 1 = ?", a model may call a Calculator tool when it should answer directly. This wastes latency and compute. The model has not learned to discriminate when tool use is necessary. You observe: correct final answers, but excessive tool calls, or latency degradation. A third failure: adversarial observations. If the tool returns false information (e.g., a web search returns misinformation), the model trusts it and propagates the error. Robustness requires the model to detect contradictions between tool outputs and internal knowledge, and to fall back to reasoning or multi-source verification. Without this, tool-using agents become less reliable than base models on poisoned tools.
