The Agent Loop

An agent receives a goal, plans actions, uses tools or environments, observes feedback, tracks memory, and decides when to stop.

Ordinary Problem

Many useful tasks require doing work, not just answering a message.

Naive Picture

An agent is just an LLM with a longer prompt.

Why It Fails

The key difference is interaction. The system must act, observe consequences, update state, and continue toward a goal.

First-Principles Move

A task has state, actions, observations, constraints, and success criteria. The agent loop connects those pieces into a controllable process.

What Breaks Without It

The system gives advice without completing the task, or it drifts because it cannot track progress.

Course Role

This is the core transition from chatbot to agent in Part 1 and the recap.

Worked Example

A deep research agent is tasked with finding housing options for someone renting near Stanford. The agent receives the goal: "Find 5 suitable rental homes within 5 miles of Stanford University, with monthly rent under 3000 dollars." Step 1: The agent formulates a web search query, "rental homes near Stanford University California under 3000 per month." Step 2: It calls a search tool and receives 12 candidate listings with addresses, prices, and descriptions. Step 3: The agent observes the results, filters out 7 listings that exceed budget or distance constraints, leaving 5 candidates.

Step 4: It calls a second tool to verify distances using a maps API, confirming each property's proximity. Step 5: Based on the verified results, the agent synthesizes a summary with pros and cons for each property. Step 6: It checks its memory: goal was to find 5 homes—it has exactly 5 verified candidates—and stops. The entire workflow required 3 tool calls, 2 filtering steps, and memory tracking to detect task completion.

One Level Deeper

The agent loop is a state machine where the state S includes: (1) the goal G (find 5 homes under budget), (2) memory M (prior observations and actions taken), (3) the current observation O from the environment, and (4) a stopping condition C. At each step, the model computes the next action A from the tuple (G, S, M, O). After action A executes, the environment returns new observation O', which updates state S to S'.

The loop continues while not C(S). Concretely: S = {goal: "5 homes", memory: ["checked 12 listings", "verified 5 distances"], observation: "have 5 valid candidates"}. The stopping condition C evaluates whether the count of verified candidates equals 5 AND each satisfies budget/distance predicates. Without explicit state tracking, the agent cannot detect when the goal is achieved or avoid repeating failed actions. The loop's quality depends on memory fidelity: if the agent forgets which listings it already checked, it will re-query and cycle. The state update rule must be deterministic and observable.

Failure Boundary

The agent loop becomes untrustworthy when the stopping condition is undefined or the agent cannot reliably detect it. For example, if the stopping condition is vague ("find good homes"), the agent may never halt, endlessly searching for marginal improvements or refining the summary. If memory is lossy or incomplete (e.g., context window drops early observations), the agent may forget constraints and accept listings that violate the original budget or distance criteria. Another failure boundary occurs when the environment provides delayed or contradictory feedback: if the search tool returns 3 listings the first query and 8 the second query with overlapping results, the agent may either loop indefinitely trying to reconcile counts or stop prematurely with incomplete data.

Long-horizon agents also fail when they lose track of why they took an action—if the agent generates a tool call but cannot retrieve the reasoning that motivated it, later steps may pursue irrelevant branches. The observable symptom is repetitive tool calls with no progress toward the goal.
