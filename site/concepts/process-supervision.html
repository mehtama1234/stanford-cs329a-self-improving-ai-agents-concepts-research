Process Supervision

Process supervision evaluates intermediate reasoning steps instead of only the final answer.

Read the deep dive — seen on a real run →

Ordinary Problem

A final answer can be right for the wrong reason or wrong because of one local step.

Naive Picture

Only the final answer matters because users usually see the final answer.

Why It Fails

Final-answer labels do not tell the model which step was valid, invalid, missing, or unsupported.

First-Principles Move

If reasoning is a chain, feedback should attach to links in the chain. Step-level labels create a denser learning and debugging signal.

What Breaks Without It

Models learn to imitate final-answer style while leaving hidden reasoning errors untouched.

Course Role

Part 3 uses process supervision to explain stronger verification for reasoning.

Worked Example

A model solves a multi-step fraction problem. Step 1 is correct: "Let x be the numerator." Step 2 is correct: "The denominator is 7 less than 3 times the numerator, so denom = 3x - 7." Step 3 is correct: "Set up the equation: x / (3x - 7) = 2 / 5." Step 4 is correct: "Cross multiply: 5x = 2(3x - 7) = 6x - 14." Step 5 is correct: "Simplify: 5x - 6x = -14, so -x = -14, x = 14." With outcome supervision, a human labels only the final answer: correct. But the model learns nothing about which steps mattered.

With process supervision, each step gets a label: all five steps are marked correct. Now the model learns that each reasoning link is valid, and it sees what right reasoning looks like step by step. If step 3 had been wrong (e.g., "x / (3x - 7) = 3 / 5" by mistake), it gets marked incorrect, and the model learns: this kind of equation setup is wrong, even if the final answer happened to be right by coincidence.

One Level Deeper

A process reward model (PRM) assigns a score r_step_j ∈ [0,1] to each step j in a reasoning chain. Training pairs are (question, trajectory, step_labels) where step_labels = [l_1, ..., l_m] with l_i ∈ {correct, incorrect}. The PRM learns P(step_j is correct | question, steps_1...j). At test time, given a full solution trajectory with m steps, compute r_1, r_2, ..., r_m and aggregate—commonly via product: score_solution = Π r_j (all steps must pass).

The contrast with outcome reward models (ORM): ORM computes a single score r_final for the entire solution. PRMs produce m scores, one per step. PRM training is more data-intensive (m labels per solution vs. 1), but creates a denser learning signal. Studies show PRMs generalize better to new domains and tolerates distribution shift better than ORMs. The key computation is step-level correctness prediction, which requires the model to see both the prior reasoning context and the current step in question.

Failure Boundary

Process supervision fails when steps are labeled by non-experts or automated methods that miss subtle errors. For example, if a step looks algebraically correct but skips a crucial constraint (e.g., solving x² - 1 = 0 without checking x ≠ 1), a human-in-the-loop might catch it, but an automated labeler might score it correct. The model then learns to produce steps that pass local checks but violate global constraints.

Another failure: the model learns to hallucinate steps. If the PRM is trained but the generator is later fine-tuned against the PRM with reinforcement learning, the model may learn to output pseudo-steps that "look" correct to the PRM without actually advancing the solution. This is the "PRM gaming" failure mode. You would observe: high PRM step scores, but end-to-end solution accuracy drops, or the reasoning becomes incoherent. Mitigating this requires keeping the generator frozen during verification (use PRM only to select among frozen samples), or ensuring the PRM training includes adversarial examples where steps are syntactically correct but logically false.
